Auth (2.1–2.5) is done: `RegisterDto`/`LoginDto` (`class-validator`, email trimmed+lowercased via `@Transform`, password `@MinLength(8)`); `AuthService.register` hashes with bcrypt cost 10 and turns the Prisma `P2002` unique-violation into a 409 (`ConflictException`) rather than checking existence first (avoids a TOCTOU gap); `AuthService.login` returns only `{ accessToken }` — the `{ sub, email }` pair lives inside the signed JWT payload, not as sibling fields in the response body, despite how the backlog line reads. `JwtModule` is HS256/7-day via `JwtModule.registerAsync` reading `JWT_SECRET` from `ConfigService`. `JwtAuthGuard` (wraps Passport's `AuthGuard('jwt')`, checks the `@Public()` reflector metadata) is registered as a global `APP_GUARD` in `AppModule` — every route needs either `@Public()` or a valid bearer token, not just the ones under `/auth`; `JwtStrategy.validate` maps the payload to `{ userId, email }` (note: `userId`, not `sub`) and that's what `@CurrentUser()` returns. Provider order in `AppModule` (`ThrottlerGuard` before `JwtAuthGuard`) is what makes SD D2's guard order real — Nest runs `APP_GUARD` entries in array order. Seed script (3.1) is done: `apps/api/prisma/seed.ts`, wired via the `prisma.seed` hook in `apps/api/package.json` (`ts-node prisma/seed.ts`, run through `prisma db seed`). Two-pass by design — every file under `seed/templates/*.json` is read and validated (denomination against the Prisma `Denomination` enum, slot shape, duplicate natural-key detection within a file) *before* any DB write, so one malformed file aborts the whole run rather than leaving a partial seed. `CollectionSet` has no DB-level unique constraint on `name` (schema unchanged from 1.3) — the script emulates "upsert by name" with `findFirst({ name, isTemplate: true })` + create-or-update inside a per-template `$transaction`, matching the SD §6 "one transaction per template" call. Slots are diffed in script code against the natural key `(year, mintMark, label)`, never via Prisma's own `upsert`, because Postgres NULL-distinctness makes the DB constraint advisory for Philadelphia (`mintMark: null`) slots; matched slots are updated in place (row id stable ⇒ `CoinItem.slotId` links survive), unmatched incoming slots are inserted, and existing slots absent from the JSON are `deleteMany`'d (relies on `onDelete: SetNull` on `CoinItem.slotId`, same as 1.3). Verified end-to-end against the real Neon dev DB with a throwaway fixture: create → idempotent re-run (0 created) → in-place update of `sortOrder`/`isKeyDate` with row ids unchanged → deletion of a removed slot → malformed-file abort, all confirmed, then the fixture and its DB rows were removed. One incidental fix: `apps/api/tsconfig.build.json` now excludes `prisma/` (same as it already excluded `test/`) — `nest build` was pulling `prisma/seed.ts` into the `rootDir: ./src` program and failing with TS6059 before this. Coins CRUD (4.2) is done: `CoinsModule` (`apps/api/src/coins`) — `GET/POST /coins`, `PATCH /coins/:id`, `DELETE /coins/:id`, all scoped to `@CurrentUser()`; PATCH/DELETE 404 on an unknown id, 403 on another user's coin (same ownership-check pattern as 3.3/3.4), via a private `assertOwned` helper. `DELETE` needs no explicit unlink step — the `CoinItem` row *is* the slot link, so deleting it frees the slot on its own; `SetSlot` is untouched. `CoinsService` returns a locally-declared `CoinItemView` (Prisma-native types: `@prisma/client`'s `Denomination`, `Prisma.Decimal`, `Date`) rather than importing `packages/shared`'s `CoinDto` directly — same convention as `SetListItem`/`UserSetSummary` in 3.3/3.4. This turned out to matter, not just be a style choice: Prisma's generated `Denomination` type is a plain string-literal union (`'Cent' | 'Nickel' | ...`), not a nominal TS `enum`, so `packages/shared`'s `Denomination` enum members are assignable *into* Prisma fields (create/update `data`) but Prisma's return values are **not** assignable back into a variable typed with the shared enum without a cast — relevant again for 4.3's `LinkingService`, which will need to compare/return denominations across both type worlds. `PATCH` relies on Prisma's own "`undefined` in `data` = leave unchanged, explicit `null` = clear" semantics, which lines up with `UpdateCoinDto` (`PartialType` + `@IsOptional()`, which class-validator treats as skip-on-`null`-too) with no extra service-layer branching needed. Verified live against the seeded Neon dev DB: unauthenticated `GET /coins` → 401; `POST` with `mintMark: "P"` stored/returned as `null`; `purchasePrice` round-trips as a numeric string (Prisma's `Decimal` has a `toJSON` returning a string, so no manual serialization needed); `PATCH` with `grade: null` cleared the field while leaving `year`/`mintMark` untouched; a second user got 403 on `PATCH`/`DELETE` of the first user's coin; `DELETE` of a bogus id → 404; owner `DELETE` → 204 and the coin dropped from the list. `LinkingService` (4.3) is done: `apps/api/src/coins/linking` — a `LinkingModule` (providers/exports `LinkingService`) imported by `CoinsModule`, per SD D2/D3 it's the sole implementor of the match rule (nothing else touches `slotId` yet — that arrives with 4.4's link/unlink endpoints). `suggest(userId, coin, excludeCoinId?)` is one `setSlot.findMany` joining `CollectionSet` (denomination match) → `UserSet` (`some: { userId }`, i.e. active/pursued sets only, never a set the caller hasn't activated) with a filtered `coinItems` include (`{ userId }`, minus `excludeCoinId` when re-suggesting for a coin being edited) to derive `currentlyLinkedCoinId`; `mintMark: coin.mintMark ?? null` is the null-safe equality the PRD §6.3 convention requires (confirmed live: a `"P"`-normalized Philadelphia 1909 cent matches its `null`-mint slot, not a separate "no match" case). `CoinsService.create`/`update` call `suggest` and wrap the result in a locally-declared `CoinMutationResponse` (Prisma-native `CoinItemView` + `packages/shared`'s `SlotSuggestion` — the latter is safe to import directly since it has no enum fields, unlike the `CoinItemView`/`CoinDto` split noted under 4.2). `POST /coins` always returns `CoinMutationResponse`; `PATCH /coins/:id` returns the bare `CoinItemView` when the edit didn't touch denomination/year/mintMark, and only wraps into `CoinMutationResponse` (recomputing suggestions, with the coin's own id excluded) when one of those three actually changed — matching SD §4's "`POST` (and `PATCH` when match key changed) → `CoinMutationResponse`" line precisely instead of always returning the wrapper. Link/unlink endpoints (4.4) are done: `POST /coins/:id/link` and `POST /coins/:id/unlink`, both added to `LinkingService` rather than `CoinsService` — per SD D3 it's the sole writer of `CoinItem.slotId`, so `CoinsController` now injects `LinkingService` directly (`LinkingModule` is already imported by `CoinsModule`, so no new module wiring was needed) alongside `CoinsService`. `link(userId, coinId, slotId)` is one `prisma.$transaction` callback: fetch+check the coin (404 unknown, 403 foreign), fetch+check the slot including a `userSets: { where: { userId } }` filter to confirm the caller has actually activated its set (404 unknown slot, 403 un-activated set — same two-tier 404-then-403 shape as 3.3's `activate`), `findFirst` the current occupant (if any) to capture its id for the response, `updateMany` to null out that occupant's `slotId` (safe against 0-or-1 matches — this is what makes displacement-before-link the actual mechanism, not the `(userId, slotId)` unique constraint, which never fires because nothing is ever double-occupying by the time the final `update` runs), then `update` the target coin's `slotId` and return `{ coin, replacedCoinId }`. `unlink(userId, coinId)` is a plain ownership-checked `update` (no transaction needed — single write, nothing to displace) and is idempotent on an already-unlinked coin. Verified live against the seeded Neon dev DB with two throwaway users: linking coin A to a slot, then linking a second coin B to the *same* slot returned `replacedCoinId` = A's id and confirmed A's `slotId` was nulled out in a follow-up `GET /coins`; unlinking B then relinking it to the same slot returned `replacedCoinId: null` (no occupant to displace); a second user got 403 linking the first user's coin; a coin owner with no activated sets got 403 linking into a real slot (not just a foreign-coin case — the "pursued set" check is a separate assertion, not implied by coin ownership); bogus slot id → 404 "Slot not found"; bogus coin id → 404 "Coin not found"; non-UUID `slotId` in the request body → 400 from `class-validator`'s `@IsUUID()` on `LinkCoinDto`. E2e tests for 4.3/4.4 (4.5) are done: `apps/api/test/coins.e2e-spec.ts` activates the seeded Lincoln Wheat Cents template and covers three cases against real slot rows — a `mintMark: "P"` 1910 cent (a year with a single Philadelphia slot and no VDB variant, chosen to keep the match unambiguous) normalizes to `null` and matches exactly one suggestion; a 1909-S cent returns both the plain and VDB 1909-S slots (`isKeyDate: true` on both); and linking two coins to the same slot in sequence returns `replacedCoinId: null` then the first coin's id, with a follow-up `prisma.coinItem.findUniqueOrThrow` confirming the displaced coin's `slotId` actually went back to `null` (not just trusting the response body). Writing this test surfaced a **pre-existing, previously-undetected break in the e2e Jest config**, not something this task introduced: `packages/shared`'s `package.json` has `"type": "module"`, so once `CoinsModule`'s DTOs started importing `@coin-collector/shared` (back in 4.1/4.2), every e2e spec that boots `AppModule` — including `auth.e2e-spec.ts` and `user-sets.e2e-spec.ts`, both previously marked done — silently started failing at the Jest level (`SyntaxError: Unexpected token 'export'`). It went unnoticed because 4.2–4.4's own verification was done via live `curl` against the dev server, never `pnpm --filter api test:e2e`. Root cause: TypeScript's `NodeNext` module setting (from the shared `tsconfig.base.json`) emits real ESM for any file under a `"type": "module"` package regardless of what the *consumer* is — that's correct for production (Node 22's `require(esm)` support is why the live API never had a problem) but Jest's CommonJS-only runtime can't execute that output at all, and no amount of `ts-jest` config overrides (`isolatedModules`, inline `tsconfig: { module: "CommonJS" }`) actually changes the emitted syntax, because `ts-jest` resolves the module kind from the discovered project config keyed off the file's own package, not the override. Fixed in `apps/api/test/jest-e2e.json` with a dedicated transform entry routing anything under `packages/shared/src/*.ts` through a small custom transformer (`apps/api/test/support/shared-esm-transformer.js`, a direct `ts.transpileModule` call forcing `module: CommonJS`) instead of the default `ts-jest` entry, plus `moduleNameMapper` entries pointing `@coin-collector/shared` and its two internal relative imports (`./enums.js`, `./contracts.js`) at the package's TS sources rather than its built ESM `dist` — test-only, the real build/deploy path is untouched. All four e2e suites (`health`, `auth`, `user-sets`, `coins`) pass together after this fix; re-run `pnpm --filter api test:e2e` after any future change to `packages/shared` or its consumers to make sure this doesn't regress again.
