# "My Submissions" (`GET /catalog?submittedByMe=true`) Backlog

Source: previously scoped and explicitly deferred in [docs/system-design_v2.md](system-design_v2.md) §4.7 ("My submissions" view, line 365) — deferred alongside the related decision, also in §4.7, to reject teaching `GET /catalog` a general optional-auth mode. This doc un-defers exactly that named feature; it does not reopen or relitigate the surrounding §4.7 decisions (dedup rules, manual review, no admin UI — see "Explicitly NOT this scope" below).

## Why this came up

Discussed in chat 2026-07-31: a user asked why a coin they submitted with `status: 'pending'` wasn't showing up in their collection. Root cause (confirmed by reading the code, not assumed): it's not a read-path bug — `Ownership`/`UserSetCoin` rows have no status guard at all, so a pending coin already added to a set renders fine everywhere. The actual gap is *discovery*: the only way to get a pending coin into a set today is the one-time submission-confirmation screen shown immediately after `POST /catalog` succeeds (`apps/web/src/components/catalog/submission-confirmation.tsx`); every other surface — catalog browse, the "Add coins" picker inside the set editor — is backed by `GET /catalog`, which hardcodes `status: 'approved'` (`catalog.service.ts:39`) and so can never surface it. If a user navigates away from that confirmation screen without acting on it, the coin becomes effectively unrecoverable until an admin approves it directly in the DB.

System Design §4.7 already named the fix and declined to build it at the time: "if skipping the submission confirmation screen and losing track of a pending coin turns out to be a real recurring complaint rather than a theoretical edge case, add an authenticated `GET /catalog?submittedByMe=true` ... plus a small page listing the caller's own submissions regardless of status." That's what this backlog builds.

## Decision

Build `submittedByMe=true` as a query param on the existing `GET /catalog`, gated by a new **optional-auth** pattern — the first of its kind in this API (§4.2/§4.7 both flag today's routes as strictly either `@Public()` with no user context, or fully guarded). Scope, decided in chat:

- `submittedByMe=true` is only honored when the caller sends a valid bearer token; sent by an anonymous caller, it's silently ignored (no error) and behaves like a normal anonymous `GET /catalog` call — same "just don't apply it" handling `isTemplate`-style optional filters used in the v1 log, adapted for v2.
- When honored, it **replaces** the `status: 'approved'` filter with `submittedByUserId: <caller>` (all statuses) — this is a dedicated "my submissions, whatever their status" list, not an OR'd-in addition to the normal approved-only browse results. Matches the §4.7 line's own framing ("a small page listing the caller's own submissions regardless of status"), and keeps the existing anonymous/default behavior of `GET /catalog` completely unchanged.
- The other filters (`country`/`denomination`/`name`/`yearMin`/`yearMax`/pagination) stay applied as normal on top of it — no reason to special-case them away just because `submittedByMe` is also set.
- Response shape is unchanged (`CATALOG_COIN_SELECT` still excludes `submittedByUserId` — the privacy rule from backlog_catalog-contributions.md 1.4/1.7 isn't reopened by this feature; the frontend already knows "these are mine" because it's the one that asked for `submittedByMe=true`, it doesn't need the id echoed back).
- This is purely a *recovery* path for a skipped confirmation screen, not a replacement for it — the submission-confirmation flow (`backlog_catalog-contributions.md` 2.4) stays the primary "use it now" mechanism and is untouched.

**Current relevant state, so the tasks below don't re-derive it:** `apps/api/src/auth/guards/jwt-auth.guard.ts`'s `JwtAuthGuard` (global `APP_GUARD`) checks `@Public()` and returns `true` immediately without invoking Passport at all when present — `req.user` is never populated on a `@Public()` route today, even if a valid bearer token is sent (confirmed by reading `canActivate`, not assumed). `apps/api/src/auth/decorators/current-user.decorator.ts`'s `@CurrentUser()` just reads `request.user` and is typed to always return a defined `AuthenticatedUser` — every existing call site trusts it's used behind a real (non-`@Public()`) guard, so it can't be reused as-is for an optional case without weakening that guarantee for every other controller. `apps/api/src/catalog/catalog.controller.ts`'s `GET /catalog` handler (`findAll`) is `@Public()` with no other guard. `apps/api/src/catalog/catalog.service.ts:34-65`'s `findAll` builds its `where` with `status: 'approved'` unconditionally (line 39) alongside the existing `country`/`denomination`/`name`/`yearMin`/`yearMax` filters; `apps/api/src/catalog/dto/find-catalog-query.dto.ts` has no `submittedByMe` field and no precedent anywhere in the v2 codebase for a query-string boolean (`set-ownership.dto.ts`'s `@IsBoolean()` is body-only — a fresh `@Transform` will be needed, not a copy of an existing one). `packages/shared/src/index.ts` already exports `CatalogCoin`/`PaginatedResponse`/`CoinStatus` (backlog_catalog-contributions.md 1.5) — no new shared type needed for the response, since `submittedByMe` only changes which rows come back, not their shape.

## Backend

- [ ] 1.1 New `apps/api/src/auth/guards/optional-jwt-auth.guard.ts` — `OptionalJwtAuthGuard extends AuthGuard('jwt')`, overriding `handleRequest` to return `user ?? undefined` instead of throwing on a missing/invalid/expired token (Passport's default `handleRequest` throws `UnauthorizedException` on any of those). Always resolves truthy from `canActivate` — a bad or absent token means "treat as anonymous," not "reject the request." This is a route-level guard applied via `@UseGuards()`, not a global one — it doesn't touch `AppModule`'s `APP_GUARD` array or any other route.
- [ ] 1.2 New `apps/api/src/auth/decorators/optional-current-user.decorator.ts` — `@OptionalCurrentUser()`, structurally identical to `@CurrentUser()` but typed `AuthenticatedUser | undefined`. Deliberately a separate decorator rather than changing `@CurrentUser()`'s return type — every other controller's `@CurrentUser() user: AuthenticatedUser` call site relies on it being always-defined behind a real guard; weakening that type would push a null-check onto call sites that structurally can't hit `undefined`.
- [ ] 1.3 `CatalogController.findAll`: keep `@Public()` (global `JwtAuthGuard` still no-ops for this route) and add `@UseGuards(OptionalJwtAuthGuard)` alongside it — Nest runs the global guard first (sees `@Public()`, short-circuits to `true`) then the method-level `OptionalJwtAuthGuard` (actually attempts Passport JWT verification, populating `req.user` if a valid token is present, `undefined` otherwise, never throwing). Add `@OptionalCurrentUser() user: AuthenticatedUser | undefined` as a new handler parameter, passed through to the service.
- [ ] 1.4 `FindCatalogQueryDto`: add `submittedByMe?: boolean` — `@IsOptional()`, `@Transform(({ value }) => value === 'true')`, `@IsBoolean()` (query params always arrive as strings even under the global `transform: true` pipe, same reasoning the v1 `isTemplate` param needed — no existing v2 precedent to copy, confirm the transform actually works via the unit test in 1.6, don't just assume the pattern).
- [ ] 1.5 `CatalogService.findAll(query, userId?: string)`: when `query.submittedByMe && userId`, replace the `where`'s `status: 'approved'` with `submittedByUserId: userId` (all statuses) — keep the rest of the filter object (`country`/`denomination`/`name`/year range) applied as-is on top. When `submittedByMe` is true but `userId` is undefined (anonymous caller), ignore the flag entirely and fall back to today's `status: 'approved'` behavior — don't 401, don't silently return nothing.
- [ ] 1.6 Unit tests (`catalog.service.spec.ts`, `catalog.controller.spec.ts`): `submittedByMe: true` + a `userId` queries `submittedByUserId` and drops the `status` filter; `submittedByMe: true` with no `userId` behaves identically to `submittedByMe` unset (still `status: 'approved'`); `submittedByMe` unset behaves unchanged from today regardless of `userId`; the DTO transform turns the query string `"true"`/`"false"` into real booleans; a mocked `OptionalJwtAuthGuard.handleRequest` returns `undefined` (not a thrown error) on a missing/invalid token.
- [ ] 1.7 New `apps/api/test/catalog-submitted-by-me.e2e-spec.ts` covering what a mocked-Prisma unit test can't: an anonymous `GET /catalog?submittedByMe=true` behaves like a normal anonymous call (200, only approved coins, no 401); an authenticated call with a valid bearer token and `submittedByMe=true` returns the caller's own pending/rejected/approved submissions and *not* another user's pending coin; the same authenticated call without `submittedByMe` is unaffected (still approved-only, same as before this feature).
- [ ] 1.8 Manual/live pass against the real Neon dev DB: submit a coin via `POST /catalog` as user A (`status: pending`), confirm anonymous `GET /catalog?submittedByMe=true` doesn't include it; confirm A's own `GET /catalog?submittedByMe=true` (bearer token attached) does include it, with the normal `status: 'approved'`-only `GET /catalog` (no `submittedByMe`) still excluding it; confirm user B's `GET /catalog?submittedByMe=true` does *not* include A's coin. Clean up the throwaway users/coin afterward.
- [ ] 1.9 `pnpm --filter api typecheck`/`build`/`test`/`test:e2e`, `pnpm lint`.

**Checkpoint:** an authenticated user can reach a page listing every coin they've personally submitted, regardless of status, and use it to recover a pending coin they lost track of after skipping the submission-confirmation screen — closing the one named gap `system-design_v2.md` §4.7 had explicitly deferred. Anonymous `GET /catalog` and the existing submission-confirmation flow are both unchanged.

## Explicitly NOT this scope (resist)

- **Surfacing a caller's pending coins in the normal catalog browse or the set-editor's "Add coins" picker.** Both stay `status: 'approved'`-only, unchanged (§4.7's rejection of a general optional-auth *browse* mode stands — this backlog only adds a distinct, opt-in `submittedByMe` list, not a change to default browse behavior).
- **Any admin/review functionality.** Still manual, direct-to-DB, per §4.7 and its §6/§7 trade-off entries — this backlog doesn't touch approve/reject at all, only visibility of a user's own submissions to themselves.
- **Editing or withdrawing a pending submission from the new page.** Read-only list; if a submitted coin is wrong, that's still a manual DB fix (no `PATCH`/`DELETE /catalog/:id` exists or is added here).
- **Applying the new `OptionalJwtAuthGuard` anywhere else.** Scoped to `GET /catalog` only for now — a second use case can adopt it later, but this backlog doesn't go looking for other candidate routes.
