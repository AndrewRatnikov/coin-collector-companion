## Server waking notice on public pages (growth 1.3)

The API on Render's free plan sleeps when idle, and the first request after that takes 30–60 s. Today the public pages show only a skeleton for that whole time. After about 3 s they should say why.

- **Hook:** `useSlowLoading(isLoading: boolean, delayMs = 3000): boolean`. It returns `true` once `isLoading` has stayed `true` for `delayMs`, and goes back to `false` as soon as `isLoading` is `false`. It clears its timer on unmount and when `isLoading` flips, so a fast response never shows the notice.
- **Component:** `ServerWakingNotice` in `components/ui/server-waking-notice.tsx`: one `role="status"` (polite) line with `common.serverWaking`, 13px `neutral-700`, test id `server-waking-notice`. It renders nothing when its `show` prop is `false`. No spinner and no animation of its own.
- **Where:** add it to the existing **loading branch** of each public page, under the skeleton. Keep the existing loading test ids and markup:
  - `/catalog` (`useCatalog`), `/catalog/[coinId]` (`useCoin`);
  - `/sets/canonical` (`useCanonicalSets`), `/sets/canonical/[id]` (`useCanonicalSet`);
  - `/sets/public` (`usePublicSets`), `/sets/public/[id]` (`usePublicSet`);
  - and the landing page's ways-in counts (above).
  On detail pages, only the page's **main** query drives the notice, not secondary queries like gaps or ownership.
- **Not here:** `/glossary` is static and has no query. Signed-in pages are out of scope for 1.3.
- **No change** to `api-client.ts`: the 75 s request timeout and the single retry stay as they are. When the request finally fails, the page's existing error state takes over and the notice goes away.

## Locale on first paint (growth 1.4)

Today `<html lang="en">` is hard-coded in `layout.tsx`. `I18nProvider` always renders English first and applies a stored Spanish preference from `localStorage` after mount, so a Spanish visitor sees English text and `lang="en"` on first paint, then a flash to Spanish. Fix both by letting the server know the locale.

- **Cookie:** name `ccc-locale` (the same value as `LOCALE_STORAGE_KEY`), value `en` or `es`, `path=/`, `max-age` one year, `SameSite=Lax`. It isn't `httpOnly`, because the client writes it. Put the read, validate and write helpers in `lib/i18n/locale-cookie.ts`: `parseLocale(value: string | undefined): Locale` (anything unknown → `'en'`) and `writeLocaleCookie(locale)`. Export a `LOCALES` list from `types.ts` and validate against it, so adding Ukrainian later is one line.
- **Writing it:** `setLocale` in `I18nProvider` writes both `localStorage` and the cookie. **Migration for existing visitors:** on mount, if `localStorage` holds a valid locale and the cookie is missing or different, write the cookie from `localStorage` (and apply the locale, as today).
- **Reading it:** `layout.tsx` becomes `async`, reads the cookie with `cookies()` from `next/headers`, sets `<html lang={locale}>`, and passes `initialLocale={locale}` to `I18nProvider`.
- **`I18nProvider`:** takes an optional `initialLocale` prop (default `'en'`, so tests that render without it are unchanged) and starts its state from it. Server and client then render the same language, so there's no hydration mismatch and no English flash. Keep the effect that sets `document.documentElement.lang` for later switches. Rewrite the comment that says the first render is always `'en'`.
- **Expected side effect:** reading cookies in the root layout makes every route dynamically rendered (`ƒ` instead of `○` in the `next build` output). That's acceptable today: every page fetches its data in the browser anyway, and Step 3 (server rendering for search) will revisit rendering per route. Record this in a short ADR, `docs/adr/2026-11-16-locale-cookie-read-in-root-layout.md`: the decision, the dynamic-rendering cost, and the rejected alternative (an inline script setting `lang` before paint, rejected because the text would still be English until hydration, so `lang` and content would disagree).
- **Metadata** stays English and static in this change.
