# User-Submitted Catalog Coins Backlog

Source: [docs/prd_v2.md](prd_v2.md) Requirement 19, [docs/system-design_v2.md](system-design_v2.md) §4.7. Scope firewall = the checkpoint at the bottom: if a task isn't needed to get there, it's not this pass.

**Not part of [docs/build-roadmap.md](build-roadmap.md)'s original Week 1–3 plan** — that plan's checkpoint (browse anonymously, sign up, clone a canonical set, edit it, mark coins owned, see gaps update) is done and confirmed (`CLAUDE.md`, Week 3 Day 5, 2026-07-22). This is a small, additive feature layered on top of the already-shipped v1 core loop, decided 2026-07-25 (PRD Requirement 19). Sized at roughly a day, not a week — one migration, one new endpoint, one small form — so it isn't broken into "Day N" sections the way the original weekly backlogs are; tasks are grouped by area instead.

**Revision note:** this replaces an earlier draft that had three real gaps, caught in review before any code was written — (1) it omitted `coins.name` (`NOT NULL`, no default) from the entire submission path, which would have made every `POST /catalog` call fail at the Prisma layer; (2) it asserted the submitter could "immediately add the coin to their own sets" with no actual mechanism, when the only existing add-coins UI (`GET /catalog`-backed) would never surface a pending coin; (3) it didn't account for `packages/shared` being ESM (`"type": "module"`), which breaks Jest's unit-test runner the same way it already broke `test:e2e` in the v1 log — the unit config has none of the fixes `jest-e2e.json` already needed. All three are resolved below and folded into [System Design §4.7](system-design_v2.md#47-catalog-contribution--review-user-submitted-coins), which was updated alongside this doc.

**Current relevant state, so nothing below re-derives it:** `apps/api/src/catalog` is `catalog.module.ts`/`.controller.ts`/`.service.ts` + `dto/find-catalog-query.dto.ts` — `GET /catalog` and `GET /catalog/:id` only, both `@Public()`, no write endpoint exists yet. `Coin` (`apps/api/prisma/schema.prisma:25-44`) has `name String` with no default (line 32) alongside the natural-key fields. `scripts/import-catalog/lib/sanitize.ts` holds the only existing implementation of the mint-mark/variety normalization this feature needs to reuse, and `scripts/import-catalog/package.json` does **not** currently depend on `@coin-collector/shared`. `apps/api/package.json`'s inline `jest` unit-test config has no `moduleNameMapper`/`transform` entries for `@coin-collector/shared` — only `apps/api/test/jest-e2e.json` does (added during the v1-era e2e fix, `CLAUDE.md`). `packages/shared/src/index.ts` is a single flat file already exporting `CatalogCoin` (which already includes `name`) and `PaginatedResponse<T>`. `apps/web/src/app/sets/[id]/page.tsx`'s "Add coins" panel (line 34, `const catalogQuery = useCatalog(addCoinsFilters)`) is the only existing UI that adds a coin to a set, and it's entirely `GET /catalog`-backed — after this feature's own `status`-filter change, it will never return a pending coin. `apps/web/src/lib/hooks/use-user-sets.ts` already has `useUserSets`, `useCreateSet`, and `usePatchSetCoins` — this feature's "add to a set" flow reuses those directly rather than the catalog-search panel.

- [ ] 1.1 Move `sanitizeIdentityField` out of `scripts/import-catalog/lib/sanitize.ts` and into `packages/shared/src/index.ts`, re-exported so `scripts/import-catalog` imports it from `@coin-collector/shared` instead of its own local copy (delete the local one). Add `@coin-collector/shared` as a real `workspace:*` dependency in `scripts/import-catalog/package.json` — it currently has none, so this import would otherwise fail to resolve. Confirm `cd scripts/import-catalog && pnpm run import` still runs clean against the existing fixtures afterward — this function has a live consumer already, not just tests.
- [ ] 1.2 `apps/api/prisma/schema.prisma`: add a `CoinStatus` enum (`approved`, `pending`, `rejected`); add `status CoinStatus @default(approved)`, `submittedByUserId String?` (FK → `User.id`, `onDelete: SetNull`), `submittedAt DateTime?` to the `Coin` model, alongside the existing `name`/natural-key fields (System Design §4.1). Generate + apply a migration against the real Neon dev DB (`prisma migrate dev --name add_coin_submission_fields`). Spot-check via Prisma Studio or `psql` that every existing imported coin came through as `status = 'approved'` with `submittedByUserId`/`submittedAt` both `null` — this should require zero backfill by construction (`@default(approved)`), confirm it actually didn't.
- [ ] 1.3 `CatalogService.findAll` (`apps/api/src/catalog/catalog.service.ts`): add `status: 'approved'` to the Prisma `where` clause so pending/rejected coins stop surfacing in public browse/search. `findOne` (`GET /catalog/:id`) stays unfiltered by status — reachable by id regardless (System Design §4.7) — don't touch it.
- [ ] 1.4 New `CreateCoinDto` (`class-validator`) and a `POST /catalog` handler on `CatalogController` — no `@Public()`, so it inherits the global `JwtAuthGuard`. Field-by-field:
  - `country`, `denomination`, `name`: required strings, trimmed via `@Transform`. (`name` is easy to forget — it's not part of the natural key, but `coins.name` is `NOT NULL` with no default, so a submission without it fails Prisma's `create` outright. This was the headline bug in the previous draft of this backlog.)
  - `mintMark`, `variety`: optional strings, normalized through 1.1's shared `sanitizeIdentityField` before touching Prisma — same "normalize at the boundary" rule the import script already follows (System Design §4.3/§4.7).
  - `year`: required, `@IsInt()`, `@Min(1000)`, `@Max(<current year + 1>)` — compute the max once (e.g. `new Date().getFullYear() + 1`) rather than leaving it unbounded; note this bakes in a fixed number at class-load time, not a live per-request calculation, which is fine at this scale but worth knowing if it's ever revisited.
  - Dedup check before create: `findFirst` across **all** statuses (`approved`, `pending`, `rejected`) matching `year`/`mintMark`/`variety` exactly and `country`/`denomination` **case-insensitively** (`mode: 'insensitive'`, matching the pattern `findAll`'s `name` filter already uses) — throw `ConflictException` (409) if found. This is deliberately stricter than the raw DB constraint, which is case-sensitive and would otherwise let `"USA"` and `"usa"` coexist as two natural keys that are visually the same coin (System Design §4.7).
  - Wrap the actual `prisma.coin.create` in a try/catch mapping a `P2002` (`PrismaClientKnownRequestError`) to the same 409 — the backstop for the case-insensitive check above racing against a concurrent submission, same pattern `AuthService.register` already uses for email uniqueness (`CLAUDE.md` backlog 2.1). Don't skip this because the app-level check above exists; it's the defense-in-depth layer, not a redundant one.
  - Create with `status: 'pending'`, `submittedByUserId: <caller's id via @CurrentUser()>`, `submittedAt: new Date()`.
  - **Response must not include `submittedByUserId`** (System Design §4.7's privacy decision — `GET /catalog/:id` is public and unauthenticated, so a raw user id on a coin payload would leak submitter identity). Explicitly destructure/omit it before returning, since Prisma's `create` result includes every column by default.
  - Add `@ApiOperation`/`@ApiCreatedResponse`/`@ApiConflictResponse`/`@ApiUnauthorizedResponse` Swagger decorators, matching the per-endpoint documentation pattern already established on `HealthController`/`CatalogController`'s existing routes (`CLAUDE.md` backlog 1.5) — easy to skip by accident since this is the first genuinely new catalog endpoint since that pattern was set.
- [ ] 1.5 `packages/shared/src/index.ts`: add `export type CoinStatus = 'approved' | 'pending' | 'rejected';`; extend `CatalogCoin` with `status: CoinStatus` and `submittedAt: Date | null` — **not** `submittedByUserId` (1.4's privacy decision; keeping it off the shared type is what actually enforces "never returned," not just a controller-level omission that a future change could accidentally undo). Add a `CreateCoinRequest` type (`country`/`denomination`/`year`/`mintMark`/`variety`/`name`) for the new endpoint's request body.
- [ ] 1.6 **Prerequisite for 1.7, do this first or alongside it.** Mirror `apps/api/test/jest-e2e.json`'s `moduleNameMapper`/`transform` entries for `@coin-collector/shared` into the inline `"jest"` block of `apps/api/package.json` (the unit-test config). - [ ] 1.9 Manual/live pass against the real Neon dev DB: unauthenticated `POST /catalog` → 401 (now redundant with 1.8, run anyway as a sanity check against the real guard, not just the e2e harness). **Checkpoint:** a logged-in user can submit a coin the catalog is missing (including a name, not just its identity fields) and, through the submission confirmation itself — not the general catalog-search add-coins panel, which structurally can't see it — add it to either an existing set or a newly created one and mark it owned. It stays invisible to everyone else's `GET /catalog` browse (and shows a pending badge on its own detail page) until its `status` is flipped to `approved` directly in the database, at which point it appears in public browse/search like any other catalog coin. Verified live against the real Neon dev DB, not just typecheck-clean.

## Explicitly NOT this scope (resist)

- Any admin API or review UI — decided manual, direct-to-DB (System Design §4.7 and its trade-off entry in §6). Don't build `@Admin()` guards, an approve/reject endpoint, or a review page.
- An optional-auth mode on `GET /catalog` to surface a caller's own pending coins in normal browse — considered and rejected (System Design §4.7): nothing else in this API mixes `@Public()` with user context, and the confirmation-screen mechanism (2.4) solves the actual need without it.
- A "my submissions" list/page to recover a pending coin if the confirmation screen (2.4) is skipped — an explicit, accepted gap (System Design §4.7, §7), not an oversight. The coin isn't lost, just harder to find until it's approved; revisit only if this becomes a real recurring complaint.
- A `<select>`/autocomplete for `country`/`denomination` populated from the catalog's distinct existing values — a plausible future nicety (System Design §4.7) that would reduce cosmetic casing/spelling drift, but not required: the case-insensitive dedup check in 1.4 is what actually prevents a duplicate, not the picker.
- Image upload/attachment on a submitted coin — out of scope, same cut as user-uploaded photos generally (PRD Non-Goals, System Design §4.3). A user-submitted coin has no image.
- Fuzzy or near-duplicate matching beyond the exact (case-insensitive on country/denomination) natural key — that's the entire v1 dedup story (§4.7); a "did you mean this existing coin" suggestion UI is a plausible future nicety, not required here.
- Deleting rejected coins, ever — the schema has no `onDelete` path for `coins` and this doesn't introduce one (§4.1, §4.7); a bad rejection is fixed by flipping `status` back, not by recreating the row.
- Any change to `GET /sets/public`, set cloning, or gap-view/completion logic — none of them filter or branch on a coin's `status`, and none need to (§4.7 is explicit that review only gates `GET /catalog` discoverability).
- Moving the review mechanism to something heavier (queue, notifications, etc.) — only reconsider per System Design §7 if submission volume genuinely outgrows manual review, not preemptively.
